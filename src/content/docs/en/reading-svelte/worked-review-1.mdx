## The feature

The prompt was: *"Build a todo list with add/rename/toggle, an undo history, a filter bar, a completed-count badge, and a stats panel showing how many are active."* The result below is the kind of first draft an AI assistant hands back for a small Svelte 5 feature — every file uses `$props()`/`$state`/`$derived` somewhere, so the whole project (forced into runes mode by this course's own `vite.config.ts`, same as every AI-generated project since Svelte 5.0) treats every file as runes-mode code. Read it in this module's [reading order](/svelte/en/reading-svelte/): runes vs legacy mode first, then who owns each piece of state, then props/bindings/snippets, then events and the DOM, then keys. It has **6 real bugs**, from four different categories, and two of them are hard compile errors `svelte-check` catches immediately — the other four compile clean and only misbehave.

<script lang="ts">
  import type { Filter, Todo } from './types';
  import TodoList from './TodoList.svelte';
  import TodoStats from './TodoStats.svelte';
  import CompletedBadge from './CompletedBadge.svelte';

  let todos = $state<Todo[]>([]);

    history.push(todos.map((t) => ({ ...t })));

    todos.push({ id: String(nextId++), text, done: false });

    if (prev) todos = prev;

## The review walk

### Runes vs legacy mode: `export let` and `$:` mixed into a runes file

`TodoStats` mixes Svelte 4's `export let`/`$:` reactivity primitives into a project that is in runes mode everywhere (any rune anywhere in a file — or, as here, a project-wide `runes: true` compiler option — puts that file in runes mode). This is the single most common shape of AI-generated Svelte bug, and it is not a soft warning:

<SpotTheBug code={`export let todos: Todo[];
$: activeCount = todos.filter((t) => !t.done).length;`}>
Both lines are hard compile errors the instant the file is in runes mode — not "unexpected but tolerated," a real, blocking `svelte-check` error:

```text
Error: Cannot use `export let` in runes mode — use `$props()` instead
https://svelte.dev/e/legacy_export_invalid
```

Removing just the `export let` line and re-checking the file shows the *second* legacy primitive is its own, independent hard error too — the compiler does not stop at "one legacy pattern is enough to flag," each one is checked and rejected on its own:

```text
Error: `$:` is not allowed in runes mode, use `$derived` or `$effect` instead
https://svelte.dev/e/legacy_reactive_statement_invalid
```

This exact pair is already proven end-to-end, with the real thrown text from `compile()` itself, in [Events & Attributes](/svelte/en/foundations/events-and-attributes/) — this SpotTheBug reproduces it against this feature's own file. The fix is `$props()` and `$derived`, shown below.
</SpotTheBug>

### Who owns this state: an `$effect` writing a value `$derived` should own

`CompletedBadge` computes `doneCount` — a value entirely derivable from `todos` — by writing it into a separate `$state` variable from inside an `$effect`.

<SpotTheBug code={`let doneCount = $state(0);
$effect(() => {
  doneCount = todos.filter((t) => t.done).length;
});`}>
This compiles clean and looks correct on every render you'd check by eye. The [`$effect` Rune](/svelte/en/reactivity/effect-rune/) lesson proves the concrete cost with a running test: the mirrored value is genuinely, measurably **stale** for a window between the triggering write and the next flush, in a way `$derived` never is. Reproduced here against this exact pattern:

```text
✓ CompletedBadge: re-syncs doneCount through a whole extra $effect commit on every todos change
✓ bare-state proof: mirroring a derived value via $effect lags one flush behind $derived

Test Files  1 passed (1)
     Tests  2 passed (2)
```

The fix is deleting the `$effect` and the separate `$state` variable entirely: `let doneCount = $derived(todos.filter((t) => t.done).length);` recomputes the instant it is read, with no lag and no second place for the value to live.
</SpotTheBug>

### Who owns this state: mirroring a prop into `$state`

`EditableLabel` copies the `text` prop into a local `draft` at mount, to give the input something to edit locally before saving.

<SpotTheBug code={`let { text, onSave } = $props();
let draft = $state(text); // mirrors the prop once, at mount`}>
`$state(text)` reads `text` exactly once — at the moment this line runs — and never again. `svelte-check` even calls this out on its own, unprompted:

```text
Warn: This reference only captures the initial value of `text`. Did you mean to reference it inside a closure instead?
https://svelte.dev/e/state_referenced_locally
```

But the warning is easy to dismiss as noise, so prove the actual behavior: if `text` changes from OUTSIDE this component later — an undo restoring a previous version of this exact todo, the most realistic trigger here — `draft` does not follow it.

```text
✓ EditableLabelBad: does not resync draft when the text prop changes from outside (e.g. undo)

Test Files  1 passed (1)
     Tests  1 passed (1)
```

The fix keeps the local edit-buffer (a real design need — you can't safely bind directly to an immutable prop while typing) but resyncs it whenever the upstream value changes, and silences the warning honestly with `untrack` (shown in the corrected code below) rather than ignoring it.
</SpotTheBug>

### Props, bindings, and snippets: a `{#snippet}` that is never `{@render}`ed

`TodoApp` defines an `emptyState` snippet for when the filtered list is empty, but never actually renders it anywhere.

<SpotTheBug code={`{#snippet emptyState()}
  <p>No todos match this filter.</p>
{/snippet}

<!-- ...TodoList is always rendered, unconditionally, regardless of visible.length -->`}>
A `{#snippet}` block is a value, not a side-effecting declaration — defining it does nothing on its own; only `{@render name()}` puts its markup on the page. Nothing about this fails to compile or warns: the snippet is simply dead code, and the empty-filter case renders an empty `<ul>` with no explanation.

```text
✓ EmptyStateBad: never shows the empty-state snippet because it is declared but never {@render}ed

Test Files  1 passed (1)
     Tests  1 passed (1)
```

The fix is an `{#if visible.length === 0}{@render emptyState()}{:else}...{/if}` around the two branches, proven in the [Snippets & Render](/svelte/en/components/snippets-and-render/) lesson to be the actual contract a snippet's name carries.
</SpotTheBug>

### Events and the DOM: `on:click` instead of `onclick`

The filter buttons use the Svelte 4 event-directive syntax.

<SpotTheBug code={`<button aria-pressed={filter === f} on:click={() => (filter = f)}>{f}</button>`}>
Unlike `export let`/`$:`, this is real, working syntax that the compiler still recognizes and lowers correctly — it degrades to a deprecation warning, not an error:

```text
Warn: Using `on:click` to listen to the click event is deprecated. Use the event attribute `onclick` instead
https://svelte.dev/e/event_directive_deprecated
```

The fix is `onclick`, a plain property like every other Svelte 5 event handler, proven with the full legacy-recognition table in [Events & Attributes](/svelte/en/foundations/events-and-attributes/).
</SpotTheBug>

### Keys and identity: a keyless `{#each}` with a stateful child

`TodoList` iterates `todos` with no `(todo.id)` key, and each `TodoItem` holds its own local `selected` state — purely local, tied to nothing in the data.

<SpotTheBug code={`{#each todos as todo}
  <TodoItem {todo} {onToggle} {onRename} />
{/each}`}>
Without a key, Svelte reuses each list position's existing component instance — and whatever local state it holds — by **position**, not by the todo's identity. As long as the list never reorders, this looks completely fine. The moment an item is prepended — exactly what "Undo" and this app's own history can do — the OLD row's local state (its `selected` checkbox) stays attached to whatever item now happens to sit at that same index.

```text
✓ TodoListBad (keyless each): bleeds per-row selection to the WRONG row after prepending an item

Test Files  1 passed (1)
     Tests  1 passed (1)
```

The fix is `{#each todos as todo (todo.id)}` — a stable id from the data, never the row's current position.
</SpotTheBug>

## What changed and why

| # | Bug | Category | Fix |
|---|---|---|---|
| 1 | `export let`/`$:` mixed into a runes-mode file | Runes vs legacy | `$props()` + `$derived` — both legacy forms are hard compile errors, not warnings |
| 2 | `$effect` writing `doneCount` instead of deriving it | State ownership | Delete the `$effect` and the separate `$state`; use `$derived` |
| 3 | `$state(text)` mirrors a prop once, never resyncs | State ownership | Resync via `$effect`; silence the (correct) warning with `untrack` |
| 4 | `{#snippet emptyState}` defined, never `{@render}`ed | Props/bindings/snippets | `{@render emptyState()}` inside an `{#if visible.length === 0}` |
| 5 | `on:click` on the filter buttons | Events & DOM | `onclick` — the same syntax, deprecated but still working |
| 6 | Keyless `{#each todos as todo}` with a stateful `TodoItem` | Keys & identity | `{#each todos as todo (todo.id)}` |

## Mental Model

Two of these six bugs never reach runtime at all — `svelte-check` refuses to compile them, because runes mode and legacy mode are two separate compiler passes that cannot be merged. The other four all compile clean and all look correct on a single render: an effect-mirrored value is wrong for a window most manual testing never lands in, a mirrored prop is wrong only after a second, external change, a dead snippet is wrong only when the list happens to be empty, and a keyless list is wrong only after a reorder. Reading the code once proves almost nothing about any of the last four; only running it — a real `svelte-check` pass plus a real `vitest` run against fake reorders and prop updates — does.

## Common Misconceptions

- **"If it's in a `.svelte` file, `export let` and `$state` can mix — Svelte figures it out."** Proven false, twice, with the real error text: the moment any rune appears anywhere in a file (or the project forces runes mode), `export let` and `$:` are hard compile errors, not a softer "pick one" warning.
- **"A `$state` variable initialized from a prop stays in sync with that prop."** Proven false: `$state(text)` reads `text` exactly once. Svelte's own compiler even warns about this specific line — `state_referenced_locally` — which is worth trusting rather than dismissing.
- **"Defining a `{#snippet}` is enough to make it appear."** A snippet is a value; only `{@render name()}` puts it on the page. An unrendered snippet produces no error, warning, or console output of any kind.
- **"A missing list `key` only matters for performance."** Proven false with a reorder test: without a key, an unrelated row's local state (here, a selection checkbox) follows the list *position*, not the data — a correctness bug, not a performance one.
