## The feature

The prompt was: *"Build a dashboard with a threshold slider to filter data points, a chart widget showing the top point, a tooltip on the slider, an async 'total' stat, and legend settings the user can toggle."* This draft leans on four Svelte 5 features an AI assistant reaches for constantly — `bind:`, `use:` actions, `$state.raw`, and `await` in the template — and gets the *contract* of every single one slightly wrong. Read it in this module's [reading order](/svelte/en/reading-svelte/): after runes vs legacy and state ownership (this review's predecessor), the next two steps are props/bindings/snippets and events/DOM — exactly where four of these **5 real bugs** live. Two are hard compile errors.

## The review walk

### Props, bindings, and snippets: `bind:` to a non-`$bindable` prop

`RangeFilter` never opts its `min` prop into two-way binding, but `Dashboard` binds to it anyway.

<SpotTheBug code={`<!-- RangeFilter.svelte -->
let { min }: { min: number } = $props();

<!-- Dashboard.svelte -->
<RangeFilter bind:min={threshold} />`}>
A prop flows one way unless the child explicitly grants a two-way surface with `$bindable()`. This is a real, caught `svelte-check` error that names the exact fix — not a silent no-op:

```text
Error: Cannot use 'bind:' with this property. It is declared as non-bindable inside the component.
To mark a property as bindable: 'let { min = $bindable() } = $props()' (ts)
```

The fix is `let { min = $bindable() }: { min: number } = $props();` inside `RangeFilter` — proven in the [Bindings](/svelte/en/bindings-actions-transitions/bindings/) lesson to be required before any `bind:` to a component prop is legal.
</SpotTheBug>

### Events and the DOM: a `use:` action that never re-runs

`tooltip` sets `node.title` once, at mount, from whatever `text` happened to be at that moment.

<SpotTheBug code={`export function tooltip(node: HTMLElement, text: string) {
  node.title = text; // set once at mount
}`}>
An action's function body runs exactly once, when the element mounts. Unless it returns an `update(newArg)` method, Svelte has no way to know the argument even *can* change — and `visible.length` here changes every time the threshold slider moves.

```text
✓ TooltipButtonBad: never updates node.title after the text prop changes — no update() on the action

Test Files  1 passed (1)
     Tests  1 passed (1)
```

The fix is returning `{ update(newText) { node.title = newText; } }`, proven in the [Actions](/svelte/en/bindings-actions-transitions/actions/) lesson to be the one thing that makes an action's argument actually reactive (an `@attach` attachment gets this for free, re-running on every reactive read, which is why this course's Actions lesson recommends attachments for new code — `use:` remains for library interop).
</SpotTheBug>

### Props, bindings, and snippets: `await` in a template with no `experimental.async`

`AsyncStat` awaits directly in a template expression.

<SpotTheBug code={`<p>Total: {await load()}</p>`}>
`await` in a template, a `$derived`, or at a component's top level is a real compile error unless the project turns on an experimental compiler flag — most AI-generated code never mentions it, because it predates this feature:

```text
Error: Cannot use `await` in deriveds and template expressions, or at the top level of a component, unless the `experimental.async` compiler option is `true`
https://svelte.dev/e/experimental_async
```

With `experimental.async: true` (this course's own `vite.config.ts` already sets it project-wide, same as the [Async Svelte](/svelte/en/reactivity/async-svelte/) lesson proves), the identical source compiles with zero errors and zero warnings. The fix here isn't changing the component at all — it's making sure the project the AI generated this for actually has the flag on, and wrapping the await in a `<svelte:boundary pending>` for loading UI (shown in the corrected code).
</SpotTheBug>

### Keys, transitions, and boundaries: no `<svelte:boundary>` around a widget that throws

`ChartWidget` throws when `points` is empty (`Math.max()` of nothing is `-Infinity`, and no point's value equals it, so `.find()` returns `undefined` and `top.label` throws). `Dashboard` renders it with no boundary at all.

<SpotTheBug code={`<h2>Dashboard</h2>
<ChartWidget points={visible} />
<!-- no <svelte:boundary> anywhere -->`}>
By default, an error thrown while rendering unmounts the **entire nearest root**, not just the failing widget — an empty filter result (a completely normal, reachable state, not an edge case) takes down the whole dashboard, including the slider and the async stat that have nothing to do with the chart.

```text
✓ DashboardNoBoundaryBad: an empty points array crashes the WHOLE dashboard, uncaught

Test Files  1 passed (1)
     Tests  1 passed (1)
```

The fix, proven in the [Lifecycle](/svelte/en/components/lifecycle/) lesson's full `<svelte:boundary>` coverage, is wrapping just `ChartWidget` in a boundary with a `{#snippet failed}` — the rest of the dashboard survives untouched.
</SpotTheBug>

### State ownership: `$state.raw` mutated instead of reassigned

`ChartSettings` mutates a property of a `$state.raw` object directly.

<SpotTheBug code={`let options = $state.raw({ color: 'teal', showLegend: true });
function toggleLegend() {
  options.showLegend = !options.showLegend; // mutation
}`}>
`$state.raw` opts out of the deep-reactive Proxy wrapper — proven in the [`$state` Rune](/svelte/en/reactivity/state-rune/) lesson, only whole-cell **reassignment** counts as a write; mutating the contents changes the data in memory but never notifies anything, so the UI silently never updates:

```text
✓ ChartSettingsBad: mutating $state.raw in place does not trigger a re-render

Test Files  1 passed (1)
     Tests  1 passed (1)
```

The fix is `options = { ...options, showLegend: !options.showLegend }` — a brand-new object, which `$state.raw` does react to.
</SpotTheBug>

## What changed and why

| # | Bug | Category | Fix |
|---|---|---|---|
| 1 | `bind:min` to a prop never marked `$bindable()` | Props/bindings/snippets | `let { min = $bindable() } = $props()` |
| 2 | `use:tooltip={text}` with no `update()` | Events & DOM | Return `{ update(newText) {...} }` from the action |
| 3 | `await` in the template with no `experimental.async` | Props/bindings/snippets | Enable the flag project-wide; gate the await in `<svelte:boundary pending>` |
| 4 | No `<svelte:boundary>` around a widget that can throw | Keys/transitions/boundaries | Wrap just `ChartWidget` in a boundary with `{#snippet failed}` |
| 5 | `$state.raw` object mutated in place | State ownership | Reassign a new object instead of mutating the old one |

## Mental Model

Every bug in this review is a **contract violation**, not a syntax mistake: `bind:` assumes the child opted in, `use:` assumes the action re-runs the way a reactive prop would, `await` in a template assumes an experimental flag is on, and mutating `$state.raw` assumes the same reactivity `$state` gives you for free. Two of the five contracts are enforced by the compiler itself (bind, await); the other three are silent, and only a running probe — an actual reorder, an actual re-render count, an actual thrown error — reveals which one was broken.

## Common Misconceptions

- **"`bind:` always works if the child has a prop with that name."** Proven false with a real `svelte-check` error: a prop is one-way by default, and `bind:` to it is rejected unless the child wrote `$bindable()`.
- **"A `use:` action's argument is reactive automatically, like a prop."** Proven false: without an `update()` method, the action's function body runs once, at mount, and never again.
- **"`await` in a template just works in any Svelte 5 project."** Proven false with the real compiler error: it needs `experimental.async: true` explicitly, and is still labeled experimental.
- **"If a widget can throw, wrapping the whole page in one `<svelte:boundary>` is enough."** Technically true, but it means *any* failure anywhere unmounts the *entire* page. This review's fix scopes the boundary to just the widget that can actually fail.
- **"`$state.raw` still lets you mutate nested properties, it just skips deep proxying for performance."** Proven false: mutating it is not merely "less optimized," it is silently ignored by the reactivity system entirely.
